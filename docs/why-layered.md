# 为什么要先分层，再动手

这篇是 `pi-magpie-ops` 的方法论底稿。案例在 `skill/references/`，这里讲**为什么这么查**。

---

## 一、症状会骗人，层次不会

「慢」和「不生效」这两个症状，在整条链的**每一层都能产生**。而且看起来一模一样：

| 层 | 同样的症状「慢」可能来自 |
|---|---|
| ① agent 接线 | 本地挂着一堆直连 provider，启动时逐个探测（实测 34s → 清理后 7~8s） |
| ② 网关路由 | `routing=order` 第一位是个半死 provider，每次都死等（实测 343s → 排序后 2.4s） |
| ③ 上游 provider | 配额耗尽、被墙、上游自己抖动 |

**如果你不先定位层次，就会在最贵的地方修最便宜的 bug**——
比如删掉一个完全健康的 provider，或者去调 agent 的配置，而真正的问题在网关的成员顺序上。

所以第一步永远是：

```
网关活着吗 → 接线指对了吗 → 这条路上有谁 → 真发一次请求看耗时和实际服务者
```

前三步都是**只读**的，加起来不到 10 秒。

## 二、`/v1/models` 是排查中最危险的假证据

这是本仓库最想强调的一条。

`GET /v1/models` 返回 200、里面有 62 个模型 id、你要的那个名字也在里面——
**这不构成任何「provider 健康」的证据。**

它只说明：**本地配置里登记了这个模型**。它不校验上游能不能连、配额够不够、会不会超时。

真正算证据的只有一条：

```bash
magpie provider test <id>              # 或者真发一次完成请求
```

**推论：任何删除动作，都必须建立在真调失败之上。** 否则你删掉的可能是唯一还能用的那个。

---

## 三、`order` 模式和「半死」的陷阱

`routing=order` 的语义是「严格按列表顺序发，失败了下一位」。

这里有两个容易误判的点：

1. **没有「先探测再选」机制。** 它不会先去 ping 一下第一个成员。它是直接发请求，
   然后等。所以**顺序 = 优先级**，不是「候选池」。
2. **failover 只在请求真的失败时触发。** 而「能连上但 5 分钟才回」**不算失败**。

于是最坑的状态不是「provider 挂了」，而是「provider 半死」：

| 状态 | `order` 模式下的行为 |
|---|---|
| 完全挂掉（连接被拒 / 立刻 4xx） | 快速 failover 到下一位，**用户几乎无感** |
| **半死（能连上，极慢）** | **一直等，永不 failover**，用户全程卡住 |
| 健康 | 正常 |

**所以 `order` 列表的第一位，必须是你实测过最快的那个。** 这不是优化，是正确性要求。

`order` 之外的 `smart` 模式则会挑「订阅还有额度、且最先重置」的那位，
在多次订阅的场景下通常更省心，但它也有自己的偏好逻辑，不是「最快」。

## 四、证据的等级

排查中不同信息源的可靠性差很多。按可信度从高到低：

| 等级 | 证据 | 为什么 |
|---|---|---|
| **A** | 真实请求的返回体 + 耗时 | 唯一能反映端到端实际行为的东西；返回体里的 `"model"` 揭示真正服务者 |
| **B** | `magpie provider test <id>` | 真的往上打了一次，但只覆盖指定的 provider/model |
| **C** | `magpie healthcheck` / `GET /v1/models` | **只证明网关进程在答**，与上游无关 |
| **D** | 看配置文件的字面内容 | 只说明「打算这样」，不说明「实际这样」。网关有内存态，可能与磁盘不一致 |
| **E** | 「昨天还好好的」 | 不是证据 |

**实践含义**：报告结论时必须说清自己处在哪一级。
「`/v1/models` 里有它」和「它现在能用」是两句完全不同的话。

## 五、归属先于修改

一次真实的排查失误：在一个桌面端里死活找不到 `favoriteModels` 这个配置项，
改了也没反应。最后发现——**那根本不是这个软件的配置**，是另一个同名目录下的另一个软件写的。

教训：**当你怀疑某个配置项不生效时，第一件事是证明它属于谁，而不是继续改它。**

验证方法不用猜（`skill/references/04-desktop-collision.md` 有完整命令）：

1. 在该程序的 asar / 二进制里做**字节扫描**，看它到底认不认识这个键；
2. 扫描前先用一个必然存在的词做**阳性对照**（否则「0 命中」可能只是你扫错了）；
3. 用 `debug.log` / 文件 mtime 与该程序最后运行时间对账。

三条都能对上，才算确认归属。

## 六、为什么脚本是只读的

一个「体检」脚本如果能顺手改配置，它就不再是体检工具了——它会变成一个
**你不敢随便跑的、带着未审慎副作用的**东西。

所以本仓库的两个脚本严格只读：

- 不写任何文件
- 不执行任何有状态的 magpie 子命令（只用 `providers` / `groups` / `ls` / `healthcheck` 这类查询）
- 唯一的写操作是一次 `POST /v1/chat/completions`，用于拿真实延迟和实际服务模型——这是 A 级证据的来源，且 `max_tokens` 被硬性限制在几十个 token

**先看，再决定改什么。** 改的时候人应该在场。

## 七、把经验变成检查清单

这一层的价值不在「我知道怎么修」，而在「**任何人按这个顺序都能修**」。

所以每条铁律都写成了可执行形式，而不是建议：

```
1. 改前先备份          → magpie backup / Copy-Item，路径写下来
2. 优先用 CLI          → 不手改 providers.json
3. 删前必须真调验证    → off（暂时不用） vs rm（已经死了）
4. 用户点名要留的不删  → 无论健康与否
5. 改完必须自己复测    → healthcheck + 真请求 + 接线复核
6. sqlite 有锁         → 快照副本 + busy_timeout + integrity_check
```

第 3 条和第 4 条是这次排查里最贵的两条经验——
**大部分「清理」造成的故障，都是把「暂时不用」误判成「已经死了」。**
